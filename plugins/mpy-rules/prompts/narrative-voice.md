# Review Dimension: Narrative & Voice

Your task is to review the prose a change introduces: code comments,
docstrings, and commit messages. Not their format, which another dimension
covers, but whether they describe the code as it now stands, stand on their
own, and read like the rest of the repo.

Prose is the part of a diff that no compiler checks and no test catches. A
wrong comment outlives the person who wrote it and misleads every reader after.

## Before Reviewing

1. Read `CODECONVENTIONS.md` at the MicroPython repo root.
2. Read the surrounding comments in each changed file, and in the files
   nearest to it. These are your style baseline, not any external guide.
3. Read `git log` for the changed files, not just the branch:
   `git log --format='%s%n%n%b' -20 -- <file>`. This is the commit message
   baseline.
4. Note the comment density of the surrounding code. MicroPython comments
   sparsely; a diff far denser or sparser than its neighbours is worth a look.

Use Read, Glob, and Grep to examine these files.

## Review Criteria

### 1. Snapshot, Not Journey

Comments and docstrings describe what the code is, what it guarantees, and why
any non-obvious decision was made. They must not narrate development history.

Flag comments that:
- Describe what the code used to do, or what changed: "previously X, now Y",
  "changed from", "no longer", "this used to".
- Reference the act of changing: "new", "updated", "added", "moved here",
  "refactored", "now handles".
- Reference a fix or its absence: "workaround for", "temporary", "fixes the
  bug where", "TODO: this was broken because".
- Describe alternatives that were tried and abandoned.
- Reference a PR, issue or review comment as the reason, without stating the
  reason itself. A link is not an explanation.

A reader with no access to the history must understand every comment from the
code alone.

The bar for commit messages differs. A commit message describes what the change
makes true and why, in the context of the current state. That is not the same as
narrating the process: "first I tried X, then switched to Y" belongs in neither.

### 2. Self-Contained Against the Code

For each comment in the diff, ask whether it can be understood by someone
reading only the surrounding function.

Flag comments that:
- Depend on knowing what the diff changed.
- Name a variable, function, register or constant that no longer exists, or
  that the diff renamed.
- Contradict the code beneath them. Read both; do not assume the comment is
  right.
- State a value, address, size, or limit that the code does not bear out.
  Verify numbers against the code or the datasheet where you can.
- Are stale for a reason the diff introduced, even if the comment line itself
  is unchanged. A comment above a modified line is inside your scope.

### 3. Voice Matches the Repo

The style baseline is the code around the change, not any general notion of
good comments. MicroPython comments are terse, lowercase-leaning, and
explanatory only where the code is genuinely unclear.

Flag prose that:
- Explains what the code plainly says. `// increment the counter` above `i++`.
- Is markedly more verbose or more formal than its neighbours.
- Uses heading-style structure, bullet lists, or section dividers inside a C
  comment where the file has none.
- Adopts a tutorial or apologetic register: "Note that...", "It's important to
  understand that...", "We simply...".

### 4. AI Writing Markers

Text generated by an assistant carries recognisable habits. These are worth
flagging on their own, because they read as inauthentic to maintainers and
because they usually accompany padding.

Flag:
- Vocabulary that is rare in this repo but common in generated text:
  "comprehensive", "robust", "leverage" as a verb, "streamline", "facilitate",
  "delve", "ensure" used as filler, "seamless", "elegant", "crucial", "vital".
- Em-dash characters. MicroPython prose uses a plain hyphen or a comma.
- Three-item lists where the content does not naturally have three parts.
- Uniform sentence rhythm across a whole comment block.
- Hedging filler: "it's worth noting that", "generally speaking", "in essence".
- A closing sentence that restates the paragraph above it.
- Commit bodies that summarise the diff file by file. The diff is already
  visible; the body exists to say why.

Do not flag a word merely because it appears on this list. Flag it when it is
doing no work, or when the surrounding code would have said it differently.
Check the repo before you flag: `git grep -c '<word>' -- '*.c' '*.h'` tells you
whether a term is genuinely foreign here.

### 5. Commit Message Substance

Format is checked elsewhere. Judge content:
- Does the subject describe the effect of the change, or only the mechanism?
- Does the body explain why, or does it restate what the diff shows?
- Would this message help someone who hits this commit in `git bisect` five
  years from now?
- For a fix, does it say what was wrong, in terms of observable behaviour?
- Does the message claim testing or verification that the branch does not
  show evidence of?

## Calibration

This dimension attracts false positives more than the others, because prose
judgement is subjective and because a reviewer looking for AI-tells will find
patterns in ordinary human writing. Guard against that:

- Quote the exact text you are flagging. A finding without a quote is not
  actionable.
- Say what the surrounding code does differently, with a file and line
  reference to a comment you are treating as the baseline.
- Never flag a comment solely for being long. Length is only a problem when
  the content is redundant or wrong.
- Never flag on suspicion of authorship. The question is whether the text
  serves a reader, not who or what wrote it.
- Prefer `nitpick` unless a comment is actively wrong or misleading, which is
  `blocking`. Style mismatch is a `suggestion` at most.

## Output

Return findings as a JSON array following the schema in shared-context.md, with
`dimension` set to `narrative-voice`. Quote the offending text in
`description` and give the replacement wording in `recommendation`, as a
`suggestion` block where it is a single line.

For commit message findings, set `file` to the path the commit primarily
touches and cite the commit hash, since commit prose has no line number.

End with a 2-3 sentence summary.
